== Scope and honest outcomes

The new controls are suite-side regression coverage, not deployed consumer repairs.
`check-lock-pin-contract.sh` checks lock *representation* only; it does not
verify remote existence, workflow closure, allowlist admission, or policy validity.
Keep the existing lock verification and `tests/lock-transitive-closure.sh`.
A passing fixture or public-corpus probe is not proof of a working consumer job.

Both helpers distinguish `0` (accepted/verified success), `1` (invalid lock
representation or official failed analysis), and `2` (inspection unavailable or
no trustworthy verdict). GitHub Actions treats either nonzero code as a failed
step; the log preserves why. Do not use `continue-on-error` to hide either class.

== Official app verification without a second scanner

`actions/sonarcloud-result-check` queries the check-runs API with `checks: read`
for an explicit repository and exact commit. It accepts only:

* Check name `SonarCloud Code Analysis`.
* Official app ID `12526`, slug `sonarqubecloud`.
* The requested `head_sha`.
* The newest matching check-run ID, not an older success or a late start time.
* Completed `success` (pass) or `failure` (genuine official failure).

Missing, queued, pending, skipped, neutral, cancelled, timed-out, unknown, wrong
publisher, wrong commit, malformed responses and API failures cannot pass.
The poll budget is 0..300 seconds (default 180), with each paginated API request
separately bounded to 20 seconds plus a two-second forced-kill grace period.
A final request may extend wall time past the poll budget; bound the caller job
as well. This verifies a check receipt, not the analysis configuration, coverage,
project selection, or adequacy of the quality gate. Never substitute it for
analysis unless the official app is enabled for the exact repository and event.

Example *after this source is published, tested and approved*:

[source,yaml]
----
permissions:
  contents: read
  checks: read
jobs:
  sonar-result:
    runs-on: ubuntu-24.04
    timeout-minutes: 7
    steps:
      - uses: hyperpolymath/cicd-suite/actions/sonarcloud-result-check@REPLACE_WITH_PUBLISHED_TESTED_40_HEX_SHA
        with:
          sha: ${{ github.event.pull_request.head.sha || github.sha }}
----

The placeholder is deliberately not a usable deployment pin. This action needs
GitHub's read-only token, not `SONAR_TOKEN`; it does not analyse code itself.
Keep existing required status names until a reviewed migration maps them to the
new real result. Do not remove an Actions scan just because it is red: first prove
same-repository, same-commit official analysis, inspect event/project coverage,
and check required contexts. Fork and merge-queue event support need separate
consumer canaries. The default PR subject is the head SHA, not the synthetic merge
SHA; explicitly choose another SHA only when that is what the official app scans.
