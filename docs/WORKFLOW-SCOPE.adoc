= Workflow scope and repository naming
:status: Proposed organisation; no repository rename or consumer migration

CI/CD is one use of repository workflows. Scheduled maintenance, documentation
checks, dependency proposals, release preparation and estate audits share the
same execution, permissions, provenance and failure-reporting machinery.
Keeping these capabilities together avoids maintaining separate verification
and distribution systems for overlapping kinds of work.

== Recommended organisation

Retain `hyperpolymath/proven-cicd` as the published source coordinate while
existing consumers depend on it. Extend the capability catalogue with workflow
purposes such as CI, delivery, release, maintenance, documentation and estate
audit. These purposes complement the existing clades; they do not replace them
or imply that every capability is implemented or qualified.

Keep executable GitHub workflow entry points in `.github/workflows/`. Group
supporting specifications, examples and controls by purpose, and keep generic
actions reusable across groups. Put source-level test/benchmark evidence in
`proven-tests-and-benches`, with this suite responsible for orchestrating it and
checking its receipts. Consumers pin both dependencies explicitly.

`proven-workflows` would be a clearer eventual umbrella name than
`proven-cicd-and-workflows`, since the latter names a category alongside its
superset. A rename remains a separate migration decision. First inventory
full-SHA callers, forge mirrors, action allowlists, documentation links, package
identities and required checks; replay representative callers before changing
the advertised coordinate. A new name does not establish new assurance.

== When a separate repository is justified

Split only if a workflow family needs different maintainers, access controls,
release cadence or execution infrastructure. The distinction between scheduled
and event-triggered jobs alone is insufficient. Keep shared verdict logic and
controls in one owner even if deployment-specific adapters later split.

== Workflow acceptance contract

Every new workflow names its inputs, side effects, permissions, applicable
subjects, failure/refusal semantics, positive and negative controls, and
execution receipt. A successful setup job does not establish that the intended
subject was checked.

== Scoped Rust documentation

`rust-ci.yml` and `rust-ci-check` accept `doc_packages`, defaulting to
`--workspace` so existing consumers retain their coverage. A consumer with
optional GUI or database packages may select explicit `-p package` arguments
for its portable CLI boundary. Document the matching build, test and
documentation scope: excluded packages are not qualified by that job.
Doctests remain enabled, and a selected package's failing documentation fails
the gate.
