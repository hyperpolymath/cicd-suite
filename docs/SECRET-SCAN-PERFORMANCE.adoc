== A second, independent cost problem

The shared scanner inspected at standards commit
`1725bebd3773ea25627479f813283abf1c497a85`:

* sets the Gitleaks job timeout to 20 minutes;
* fetches full Git history with `fetch-depth: 0`;
* installs a checksum-verified Gitleaks 8.18.4 binary;
* scans both working tree and full history on each PR;
* stages an estate baseline from the reusable's own SHA and removes tooling
  checkouts before scanning.

This is a source inspection, not a timing benchmark of the caller's older
pinned revision. Repeated full-history scans can waste substantial minutes,
but that loop does not explain a zero-job run or days of waiting by itself.
Timeouts start when a job executes, not when a required context is expected.

== Proposed replacement execution model

Keep one recognisable required PR context: `scan / gitleaks`. Do not rename
it, remove it from rules, pass it with an echo, or mark failures nonblocking.
Separate fast prevention from historical discovery:

[cols="1,3",options="header"]
|===
|Lane |Contract
|PR prevention |Scan every introduced commit in the trusted base-to-head range,
including intermediate commits containing a secret subsequently deleted. Also
scan the intended checked-out content. No workflow-level path filters on the
required caller. A detector/configuration change triggers the broader audit
policy, not silent reuse of an older result.
|History audit |Full reachable history on initial onboarding, scheduled runs,
scanner/rule/baseline changes and explicit dispatch. Unresolved findings remain
tracked and escalated; scheduling them is not acceptance of known leaks.
|===

Do not use only `git diff BASE HEAD`: it misses a secret added and removed
inside the PR. Do not assume a depth-one checkout contains the complete PR
range. Resolve the trusted base and head to verified SHAs and explicitly
fetch the ancestry needed to scan *every commit in that range*. Missing
objects, an ambiguous merge base, an unrelated history or an unavailable base
must produce an explicit bounded fallback or an infrastructure failure,
never success. Measure the fetch as well as the scan.

Before moving an existing full-history security guarantee out of the PR
lane, get security-owner approval of the new coverage boundary. Require an
initial completed full audit; define what unresolved historical findings do
to readiness. If the policy requires all history at merge time, retain it
until an equivalently trustworthy incremental-history design is accepted.

== Operational budgets and measurement

Proposed initial service objectives, *not measurements achieved here*:

* Normal PR end-to-end p95 under 5 minutes; Gitleaks execution p95 under
  2 minutes on a declared representative corpus.
* PR job deadline 10 minutes; network connect and total download deadlines,
  bounded retries, scanner wall-clock deadline, plus runner cleanup margin.
* Separately record event, queue, checkout, install, config, tree scan and
  commit-range scan times; record commit/byte/file populations, scanner
  version, config digest, base/head SHAs and result. Never export secret
  values or unredacted scanner output.
* Alert within 5 minutes on a required context that has no corresponding
  running/queued job and an observed failed workflow; distinguish it from
  runner starvation, approval waits, superseded runs and a running timeout.
* Cancel superseded runs for the same PR; re-run the current head, not an old
  SHA. Keep PR cancellation groups separate from scheduled history audits.
* Avoid duplicate scanners doing identical work. Retain specialised shell
  rules only if planted controls show unique coverage beyond Gitleaks.

A cache can accelerate a verified binary download. A cache hit must never
stand in for a scan. An incremental clean-history watermark is security
state: key by repository, verified ancestry, scanner/config/baseline digests
and audited SHA, and protect it against PR-controlled writes. Do not add one
until invalidation, fork trust and tampering controls are tested.

== GitGuardian comparison

GitGuardian may be an effective replacement, but similar names do not imply
identical scan populations, detectors or trust boundaries. No GitGuardian
runtime or coverage was measured here. Compare it and Gitleaks on the *same*
corpus and planted leaks, with identical history boundaries, before claiming
one is faster at equivalent detection. Assess fork behaviour, availability,
licensing, data handling, custom estate rules, and the exact check integration
identity required by the ruleset. Do not run both permanently on every PR
without evidence that each finds something important the other misses.
